# «Селлерам» — техническое ТЗ v0.1 (MVP)

Статус: черновик 2026-10-22 · основа — бизнес-ТЗ v0.3 с правкой 2026-10-22 (за MVP вынесено то, что сервис высчитывает сам)

Документ описывает, **как** делаем MVP: архитектуру, данные, синхронизацию с площадками, расчёты, API и порядок работ. Что и зачем делаем — в бизнес-ТЗ, ссылки вида «БТЗ 8.5».

Пометка **[решение по умолчанию]** — предложено нами, можно поменять без пересмотра архитектуры. Пометка **[проверить]** — гипотеза по спеке API, подтверждаем на тестовом кабинете до разработки блока.

## 0. Границы MVP

**Входит:** подключение WB и Ozon (только чтение), синхронизация, прибыль по факту (БТЗ 8.1–8.7), сверка с отчётом и раскрытие цифр (БТЗ 8.8–8.9), деньги к возврату без находки «логистика по габаритам» (БТЗ 9), поставки, план, сигналы, Telegram, экспорт, 8 экранов.

**Не входит (БТЗ 18, п. 2–3):** справочник тарифов и расчёт влияния тарифов, цена безубыточности, цена для целевой маржи, калькулятор цены, оценки удержаний до выхода отчёта, оценки упущенной выручки в ₽.

**Главное правило расчётов MVP:** каждая денежная цифра — это либо строка из отчёта или API площадки, либо ввод продавца, либо сумма или произведение таких значений. Модели и допущений нет. Поэтому любую цифру можно раскрыть до источника (§8).

### 0.1. Что нашли в спеках API и что это меняет для бизнес-ТЗ

- **У WB есть ежедневные отчёты реализации:** `POST /api/finance/v1/sales-reports/list`, `period: daily | weekly`. У Ozon начисления по операциям приходят в `/v3/finance/transaction/list` почти сразу; есть и beta-методы `/v1/finance/accrual/by-day`. Значит, «прибыль ждёт отчёта» в MVP — это обычно задержка в **1 день**, а не неделя. Утренняя сводка показывает прибыль за вчера, если отчёт за вчера уже вышел; иначе — за последний закрытый день. Формулировку в БТЗ 14 стоит смягчить с «последней недели» до «последнего закрытого дня» **[проверить: во сколько выходит дневной отчёт WB]**.
- **Финансовые методы WB доступны только по персональному или сервисному токену** (`x-token-types: personal, service`). Шаг инструкции в БТЗ 4 «Базовый токен» для финансов не подходит. Инструкцию в модалке нужно переписать под персональный токен (до партнёрства) и сервисный (после).
- **Реклама Ozon — это отдельный Performance API со своими `client_id`/`client_secret`.** Ключ Seller API её не даёт. В модалку Ozon добавляем необязательный блок «Реклама» с двумя полями. Без него реклама Ozon в прибыли = 0 с пометкой «не подключено» **[решение по умолчанию]**.
- **Глубина истории WB:** `supplier/orders` и `supplier/sales` отдают 4 месяца, финотчёты — с 29.01.2024, `adv/v3/fullstats` — 30 дней за запрос, воронка `sales-funnel/products/history` — неделя за запрос. История за 6 месяцев (БТЗ 4) собирается из финотчётов. Заказы до −4 мес. берём из строк отчёта (`orderDt`), воронку и рекламу — окнами.

## 2. Архитектура

### 2.1. Процессы

```
            ┌──────────── PostgreSQL ────────────┐
            │  данные · очередь pg-boss · сводные │
            └───────▲──────────────▲─────────────┘
                    │              │
  apps/server  ─────┤              ├───── apps/server (worker)
  main.ts: HTTP API │              │      main.worker.ts: синк, расчёты,
  (кабинет, бот)    │              │      находки, сигналы, отправка в TG
                    │              │
  apps/frontend ──► API            └───► WB / Ozon API (только чтение)
```

- Один код, два входа: `main.ts` (HTTP) и `main.worker.ts` (задачи). В pm2 — два процесса. Тяжёлый синк не тормозит API.
- Очередь — **pg-boss** на том же PostgreSQL **[решение по умолчанию]**: без Redis, транзакционно с данными. На бету (20 продавцов, до 60 кабинетов) с запасом. Если упрёмся — переезд на BullMQ + Redis, интерфейс задач не меняется.
- Лимиты площадок соблюдает `RateLimiter` пакета. Чтобы два воркера не делили лимит одной учётки, все задачи кабинета выполняются строго по одной: `singletonKey = accountId` у pg-boss.

### 2.2. Задачи (jobs)

| Задача                    | Когда                                                              | Что делает                                                            |
| ------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------- |
| `sync.<account>.<stream>` | по расписанию потока (§4), после подключения                       | забирает данные потока, upsert, двигает курсор `SyncState`            |
| `backfill.<account>`      | один раз после подключения                                         | история 6 мес. по потокам окнами (§4.3), прогресс в `SyncState`       |
| `facts.rebuild`           | после синка финотчёта/заказов кабинета                             | пересчитывает `ProductDayFact` за затронутые дни (§6.4)               |
| `reconcile`               | после загрузки отчёта                                              | сверка §7                                                             |
| `findings.detect`         | после backfill, затем раз в сутки                                  | детекторы находок §9                                                  |
| `signals.evaluate`        | после `facts.rebuild` и синка остатков/отзывов                     | правила сигналов §10, запись `Alert`, уведомления                     |
| `tg.digest`               | каждую минуту выбирает пользователей с наступившим временем сводки | утренняя сводка §11                                                   |
| `account.purge`           | раз в сутки                                                        | удаляет данные кабинетов и аккаунтов, отключённых более 30 дней назад |

Ошибка задачи → 3 повтора с backoff. Ошибка авторизации (`MarketplaceApiError.isAuthError`) → кабинет в `ERROR`, событие `account.health` (БТЗ 4 «Здоровье подключения»), задачи кабинета на паузе до обновления ключа.

## 3. Подключение кабинетов

Расширяем `marketplace-account`.

**WB.** Токен разбираем через `decodeWbToken`; права проверяем `wbTokenAllows` по категориям. Обязательные категории MVP: `statistics`, `finance`, `contentanalytics`, `content`, `advert`, `supplies`, `commonapi`, `feedbacks` (точные ключи сверить с `wbTokenAllows`) **[проверить]**. Тип токена — `personal` или `service` (§0.1), флаг «только чтение» обязателен. Нет категории → 422 с `errors.token: «Нет доступа к разделу “Финансы”. Пересоздайте токен с этой категорией»`.

**Ozon Seller.** `Client-Id` + `Api-Key`, проверка `checkSellerKey`. Роль ключа — `Admin read only` **[проверить: точное имя роли в ответе]**.

**Ozon Performance (необязательно).** `client_id` + `client_secret`. Проверка — выпуск OAuth-токена. Хранится в том же зашифрованном `credentials` (JSON с полями `seller` и `performance`).

**После подключения:** `backfill` → экран прогресса (`GET /accounts/:id/sync` → проценты по потокам) → по завершении событие `account.ready` (Telegram и почта) и запуск `findings.detect` и `reconcile` по всей истории.

### 4.3. Правила синка

- **Сырьё храним как есть:** строка финотчёта или транзакции — нормализованные поля плюс исходный JSON (`raw jsonb`). Правки маппинга не требуют перезагрузки с площадки.
- **Курсор на поток** — `SyncState(accountId, stream, cursor, lastOkAt, lastError, backfillProgress)`. Отсюда метка «Обновлено» на экранах (БТЗ 7).
- **Площадка исправила отчёт задним числом.** Повторно читаем отчёты за последние 60 дней раз в сутки. Новые и изменённые строки → `facts.rebuild` за их дни → `reconcile`.
- **Backfill** идёт окнами от новых к старым: сначала 30 дней (первый экран готов быстро), потом остальное.
- **Деньги** — `Decimal(14,2)`, без float. ID отчётов WB — `BigInt` (спека прямо предупреждает).

## 6. Расчёт прибыли

### 6.1. Статьи формулы и источники

Каждая строка `FinLine` при записи получает `article` — одну статью формулы (БТЗ 8.5). Маппинг — справочник в коде (`finance/mapping/{wb,ozon}.ts`) с тестами на реальных строках тестовых кабинетов.

| Статья (`article`) | WB: поле строки детализации                                                       | Ozon: тип операции / начисления                            |
| ------------------ | --------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `REVENUE`          | `retailAmount` (продажа), с учётом `cashbackDiscount`, софинансирования           | `accruals_for_sale` по `OperationAgentDeliveredToCustomer` |
| `RETURN`           | `retailAmount` строк возврата (`docTypeName` = возврат)                           | возврат: `ClientReturnAgentOperation`                      |
| `COMMISSION`       | `retailAmount − forPay` минус выделенные ниже статьи; `ppvzSalesCommission`, `vw` | `sale_commission`                                          |
| `LOGISTICS`        | `deliveryService`, `rebillLogisticCost`                                           | услуги доставки, обратной логистики, last mile             |
| `STORAGE`          | `paidStorage`                                                                     | размещение                                                 |
| `ACCEPTANCE`       | `paidAcceptance`                                                                  | приёмка, обработка поставки                                |
| `PENALTY`          | `penalty`                                                                         | штрафы, декомпенсации                                      |
| `ACQUIRING`        | `acquiringFee`                                                                    | эквайринг                                                  |
| `OTHER_DEDUCTION`  | `deduction`, `additionalPayment`, `cashbackCommissionChange`                      | прочие услуги                                              |
| `COMPENSATION`     | компенсации ущерба (`sellerOperName`)                                             | компенсации                                                |
| `ADS`              | `AdDaily` (+ строки удержаний за продвижение, если есть в отчёте)                 | Performance API; строки продвижения из транзакций          |

Точный разбор полей (особенно `COMMISSION`, где WB считает через несколько полей) фиксируем после прогона на 3 тестовых кабинетах **[проверить]**. Критерий готовности маппинга — сверка §7 ≤ 0,5% на всех тестовых кабинетах.

### 6.2. Формула

На вариант товара за день:

```
profit = REVENUE − RETURN
       − (COMMISSION + LOGISTICS + STORAGE + ACCEPTANCE + PENALTY + ACQUIRING + OTHER_DEDUCTION) + COMPENSATION
       − ADS − selfPurchaseCost
       − Σ qtySold × CostPrice(на дату продажи)  (закупка + доставка + упаковка + маркировка + фулфилмент + прочие)
       − tax
```

- **Самовыкупы (БТЗ 8.4):** строки по заказам с `isSelfPurchase` исключаются из `REVENUE`/`RETURN`, выкупа и воронки. Их чистый результат (выручка − возврат денег − удержания по ним) переходит в `selfPurchaseCost`, в статью «Реклама».
- **Налоги (БТЗ 8.3),** по `TaxSetting`, действовавшей на дату:
  - УСН «доходы»: `rate × (REVENUE − RETURN)`;
  - УСН «доходы − расходы»: `rate × max(0, база)` на уровне кабинета за месяц, на товары — пропорционально выручке;
  - НДС: `(REVENUE − RETURN) × vat/(100+vat)` — управленческий, без вычетов;
  - ОСНО: НДС + `profitTaxRate × прибыль до налога`.
    Это управленческий расчёт по ставкам продавца, не модель. В раскрытии — «налог = 6% × 412 300 ₽».
- **Удержания без товара** (хранение и приёмка по поставке, штраф без артикула) кладём на уровень кабинета: `variantId = null`. В «Товарах» они не размазываются, а видны строкой «Без привязки к товару» **[решение по умолчанию: не распределяем, это было бы допущением]**. В сводке входят в прибыль кабинета.
- **Расходы бизнеса (БТЗ 8.7):** `MONTHLY` — сумма / дней в месяце × дни периода. Идут только в чистую прибыль магазина.
- **Возвраты по претензиям (БТЗ 8.5):** строки компенсаций, которые закрыли находку (§9.4), помечаются `article = CLAIM_REFUND` и показываются отдельной статьёй.

### 6.3. Закрытые и незакрытые дни

- День `closed = true`, когда по кабинету загружен финотчёт, покрывающий этот день (WB — daily или weekly; Ozon — транзакции за день и 24 ч без новых строк за этот день **[проверить]**).
- Для незакрытых дней `ProductDayFact` хранит только оперативные данные: заказы, выкупы из `supplier/sales` и отправлений, рекламу, остатки. Деньги из удержаний и прибыль = `null`.
- API отдаёт `profitClosedThrough: date`. Фронт рисует «Прибыль по 21.10, за 22.10 — ждёт отчёта площадки».
- Оценок нет нигде (БТЗ, правка 2026-10-22).

### 6.4. Предрасчёт

`ProductDayFact` — суммы по статьям и счётчики (заказы шт/₽, выкупы, отмены, возвраты, реклама, воронка, остаток на конец дня) на `variantId × date`. Пересчёт инкрементальный по затронутым дням. Экраны читают только его плюс справочники — так держим ≤ 2 с на 1 000 товаров (БТЗ 16). Агрегаты по товару, бренду, категории, кабинету — `GROUP BY` поверх, без отдельных таблиц на старте.

Изменение себестоимости или налога с датой в прошлом → `facts.rebuild` с этой даты.

### 6.5. Показатели (БТЗ 8.6)

Считаются на лету из `ProductDayFact` за период: маржа = прибыль / выручка; ROS = прибыль / выручка (до расходов бизнеса — на уровне магазина); ROI = прибыль / себестоимость; ДРР = реклама / выручка (по продажам) и реклама / сумма заказов (по заказам); CPO = реклама / заказы; выкуп = выкупы / (выкупы + отказы и возвраты), два варианта; оборачиваемость = средний остаток / продажи в день; скорость = продажи шт / дней с наличием; дней до конца = остаток / скорость; ABC — по накопленной доле 80/15/5 **[решение по умолчанию]** по выручке и по прибыли, сводный — худшая из двух букв.

## 7. Сверка с отчётом площадки (БТЗ 8.8)

Цель — поймать ошибки **нашего** пайплайна (маппинг, дубли, потерянные строки), а не площадки.

1. По каждому `FinReport` берём итоги площадки: у WB — поля из `sales-reports/list` (`retailAmountSum`, `forPaySum`, `deliveryServiceSum`, `paidStorageSum`, `paidAcceptanceSum`, `deductionSum`, `penaltySum`, `additionalPaymentSum` и др.); у Ozon — `/v3/finance/transaction/totals` за период и `/v2/finance/realization` за месяц.
2. Считаем те же итоги из нашего `ProductDayFact` (не из сырых строк: так проверяется весь путь «строка → статья → факт»).
3. Расхождение по каждой статье и по выручке в целом. Выше 2% → `MISMATCH`, сигнал «Расхождение с отчётом», задача нам (внутреннее событие в чат команды). До 2% → `MATCH`, на экран идёт фактический процент.
4. Публичный счётчик «средняя точность по всем кабинетам» — среднее `diffPct` по `MATCH`/`MISMATCH` за 30 дней (служебный эндпоинт, без авторизации, отдаёт одно число).

Ввод продавца (себестоимость, налоги, расходы) в сверку не входит — как в гарантии.

## 8. Раскрытие цифр (БТЗ 8.9)

Единый эндпоинт: `GET /analytics/breakdown?metric=&accountIds=&productId=&variantId=&from=&to=&article=`

- **Уровень 1** (`article` не задан): статьи формулы с суммами и источником — `REPORT` (из отчёта), `INPUT` (ввод продавца), `CALC` (арифметика над ними, с формулой строкой: «6% × 412 300 ₽»). У `INPUT` — ссылка на запись: себестоимость с `validFrom`, налоговая настройка, расход.
- **Уровень 2** (`article` задан): строки `FinLine` под эту статью — номер отчёта, дата, тип операции, заказ или поставка, сумма. Пагинация; `?format=xlsx` — выгрузка.
- Незакрытый день в раскрытии: «Отчёт площадки за 22.10 ещё не вышел».

Инвариант, проверяемый тестом: сумма уровня 2 = значению статьи на уровне 1 = вкладу в цифру на экране.

## 9. Деньги к возврату (БТЗ 9)

### 9.1. Устройство

Детектор — модуль `findings/detectors/<type>.ts` с интерфейсом:

```ts
interface FindingDetector {
  type: FindingType
  marketplaces: Marketplace[]
  detect(accountId: number, range: DateRange): Promise<FindingDraft[]>
}
```

`FindingDraft`: тип, кабинет, товар / поставка / заказ, сумма, уверенность (`HIGH | CHECK`), список `FinLine.id` и прочих доказательств (`evidence jsonb`), дедлайн подачи, ключ дедупликации (`type + ref`). Upsert по ключу дедупликации: повторный прогон не плодит дубли, а обновляет сумму.

`Finding`: всё перечисленное + `status (NEW | SUBMITTED | APPROVED | REJECTED | SKIPPED | AUTO_CLOSED | FALSE_POSITIVE)`, `approvedAmount`, `rejectReason`, `falsePositiveComment`, история статусов.

### 9.2. Кандидаты на v1 и данные под них

Все детекторы — сопоставление фактов, без тарифной модели. На v1 берём 2–3 типа, подтверждённых на тестовых кабинетах (БТЗ 21).

| Тип (БТЗ 9.1)               | WB                                                                                                                                         | Ozon                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 2. Потерянный товар         | `supplies/v1/discrepancies` и `SupplyItem.accepted` < `shipped`; принято, но нет в остатках, продажах, возвратах и компенсациях за N дней  | акт поставки (`supply-order/act/product/get`) vs остатки и компенсации         |
| 3. Возврат не вернулся      | строки возврата в `FinLine` (деньги списаны) без появления в остатках за N дней                                                            | `/v1/returns/list` со статусом «возвращено продавцу» отсутствует или просрочен |
| 4. Спорные штрафы           | `analytics/v1/deductions` (подмены), `measurement-penalties` + `warehouse-measurements` (замер расходится с карточкой), `penalty` в отчёте | штрафы в транзакциях по типам                                                  |

| 6. Неполученная компенсация | признанная утеря/брак без строки компенсации или с меньшей суммой                                                                          | `/v1/finance/compensation` и `decompensation` vs признанные случаи             |
| 7. Хранение без товара      | `paid_storage` по артикулу при нулевом `warehouse_remains` в тот же день                                                                   | отчёт о размещении по товарам vs остатки                                       |

Тип 1 «Логистика по габаритам» — после MVP. Исключение: если `measurement-penalties` WB прямо даёт сумму удержания за занижение габаритов, это факт, и он попадает в тип 4.

Пороги N, сроки подачи претензий, тексты шаблонов — по итогам проверки на кабинетах; хранятся в `findings/config.ts`, не в БД.

### 9.3. Претензии

- Шаблоны — Handlebars-строки на тип × площадку (`findings/templates/`), данные подставляются из находки и строк-доказательств. Без AI.
- Инструкция «куда подавать» — статический markdown на тип × площадку.

### 9.4. Автозакрытие и метрики

- При каждом синке финансов: появилась строка компенсации или сторно, которая ссылается на тот же заказ, поставку или ШК, — находка `AUTO_CLOSED`, строка помечается `CLAIM_REFUND`, если статус был `SUBMITTED`.
- Метрики (§16): доля `FALSE_POSITIVE` среди `HIGH`, доля одобренных по типам. Тип с долей ложных > 10% выключается флагом в конфиге.
- Счётчик пользы (БТЗ 9.4): `найдено = Σ amount`, `подано = Σ amount (SUBMITTED+)`, `возвращено = Σ approvedAmount`. Это суммы фактов и отметок продавца, без оценок.

## 10. Сигналы (БТЗ 12)

- `AlertRule` — код правила, пороги по умолчанию (БТЗ 12), переопределение на организацию (`Organization.settings.alerts`). Переопределение на товар — после старта (БТЗ 11.7).

## 12. Поставки и план

- **К поставке (БТЗ 11.5):** `max(0, ceil(скорость × (дни до поставки + запас) − (остаток площадки + в пути + свой склад)))`. Скорость — продажи за выбранный период / дней с остатком > 0 (дни без товара не занижают скорость). Расчёт на лету, параметры — query.
- **Приёмка WB:** подписка `AcceptanceSubscription(userId, warehouseIds, maxCoeff, dateFrom, dateTo, boxType)`. Сигнал срабатывает при появлении подходящей даты.
- **План (БТЗ 13):** выполнение = факт заказов или выручки с 1-го числа; темп = факт / прошедшие дни; прогноз = темп × дней в месяце. Прогнозы по фактическому темпу оставлены в MVP (решение 2026-10-22).

## 16. Нефункциональные требования

- **Скорость:** экраны отчётов ≤ 2 с на 1 000 товаров — за счёт `ProductDayFact` и индексов. Нагрузочный тест на синтетическом кабинете: 1 000 товаров × 365 дней.
- **Безопасность:** ключи — AES-256-GCM (уже есть), наружу не отдаются. Все запросы к площадкам — только read-методы: при сборке клиентов в синке разрешаем только `GET`, WB `x-readonly-method` и read-пути Ozon, а тест проверяет список вызываемых путей.
- **Изоляция:** каждый запрос данных фильтруется по `organizationId` через `accountId IN (кабинеты организации)` в одном месте — репозиторий `AnalyticsScope`.
- **Хранение:** сервер и БД в РФ (152-ФЗ). Удаление: `deletedAt` у кабинета или организации → через 30 дней `account.purge`; «удалить сразу» — та же задача немедленно.
- **Наблюдаемость:** winston (уже есть) + метрики задач (длительность, ошибки, 429 по учёткам) в лог; служебная страница здоровья синка у платформенного админа.
- **Качество:** юнит-тесты маппинга статей (§6.1) и детекторов (§9) на фикстурах из реальных обезличенных строк; инвариант раскрытия (§8); сверка ≤ 0,5% на тестовых кабинетах — критерий приёмки.
